# 多 Agent 协作法（Multi-Agent Collaboration Methodology）

> 版本: v1.0-draft | 来源: 实战提炼（2026-08 至 09，三端 Agent 团队 zhan-team 协作，subagent 调研整理）

## 核心思想

多 Agent 的价值**不在「专长差异」，而在「隔离 + 资源互补」**。三个协作价值来源：

1. **上下文隔离**——每个 Agent 独立上下文，可独立评审 / 投票 / 对抗，防「自我背书」；
2. **资源 / 环境差异**——OS、网络、在线时段、本机文件 / 外设的覆盖互补；
3. **角色设定**——「prompt 即角色」，orchestrator / 生产者 / 评审者 / 裁判是职能角色，按任务临时指派。

**两条硬约束**（实战沉淀）：
- **角色 ≠ 端**：不把任务专长写进 Agent 身份，每个 Agent 都是其设备上的通用执行者；专长只按项目临时指派（如代码仓指定唯一真源主写端）。
- **调度决策权恒在发起端**：任何端（含所谓「中枢」）都是执行载体，不成为单点调度器。

## 一、为何要增加 Agent（单 Agent 的局限）

| 单 Agent 局限 | 多 Agent 解法 |
|---|---|
| 单上下文系统性偏见，同机同模型评审防不住 | 跨端评审：高风险产物换隔离上下文审 |
| 单设备受 OS 限制（Windows 任务 / 本机文件 / 外设只能对应端做） | 异构端覆盖三 OS + 本机资源 |
| 单设备休眠 / 被占用，无法长时无人值守 | 24h 在线服务器端兜底定时 / 巡检 |
| 单端记忆是孤岛 | 共享记忆库 + 显式发布制 |
| 同机多轮交互快、跨端慢 | 「同机 >> 跨端」：跨端只用于资源型 / 通知型 |

**分工优先级**：①前缀认领 ＞ ②24h 在线归属 ＞ ③OS/设备专属性 ＞ ④在线与网络状态 ＞ ⑤负载。

## 二、协同什么（共享资产）

| 资产 | 机制 |
|---|---|
| 记忆 | 共享库显式发布制：hub 只做发现 + 指针，全文走对象存储；sourceTraceId 幂等键；**用户更正覆盖硬规则**（更正必须原地覆盖，绝不并行存旧事实） |
| 技能 | 共享桶 + `_index.json` 索引 + 发布后主动通知消费端 |
| 文件 | 三存边界：对象存储（主存储 / 单一事实来源）+ 静态托管（对外分发）+ 异地冷备（仅限二进制）；代码走 bare repo 真源端制 |
| 任务 | A2A 流式直连，带 task_id + contextId |
| 密钥 | 加密通道（ECDH + AES-GCM 密文经对象存储中转，A2A 只传路径） |

**11 类共享资产清单**（实例，zhan-team 协议 v1.1 附录）：

| # | 类型 | 存放前缀 | 登记要点 |
|---|---|---|---|
| 1 | 知识地图 kmap | `kmap/` | 已覆盖 |
| 2 | 技能 | `skills/<技能名>/` | version + changelog + sync_record |
| 3 | 项目调研报告 / 技术文档 | `project/<项目id>/docs/` | kind=doc |
| 4 | 模板 / 脚手架 | `project/_templates/` | kind=template |
| 5 | 数据 schema / 登记表格式 | `project/_schemas/` | kind=template |
| 6 | 评测基准 / 评估脚本 | `project/<项目id>/eval/` | 基准锁版本；脚本附验证 |
| 7 | 共享工具脚本 | `project/_scripts/` | 附验证步骤 |
| 8 | Prompt 库 / 提示词模板 | `project/_prompts/` | 带适用模型 + 失效场景 |
| 9 | 方法论 / 工作流模板 | `project/_methodology/` | 区分通用 vs 个人习惯 |
| 10 | 环境配置 / 踩坑记录 | `project/_env-notes/` | 「环境指纹 + 结论」格式 |
| 11 | 金标样本 + 事故复盘案例 | `project/<项目id>/goldset/`、`project/_cases/` | 与评测基准互补 |

**负面清单（不进共享）**：凭据/密钥；单端运行状态与配置本体；未验证的猜测笔记；开发中源码（走 GitHub）；未验证的技能/脚本。

## 三、如何协同（协议机制）

**双轨制**（核心）：
- **同机轨**（delegate）：生产评审、投票（3 隔离上下文）、专家会诊、红蓝对抗（≤3 回合）——多轮交互同机做，秒级。
- **跨端轨**（A2A）：资源路由、接力流水线（PARTIAL 中间态回执）——资源型 / 通知型任务。

**通信纪律（踩坑后的最终形态）**：
1. 单通路流式直连（废除邮箱 / inbox 机制，避免双轨混乱）；
2. 严格单发：受理即送达，永不重发原文；
3. 无受理 ≠ 未达：先探活，对端存活禁重发；
4. 查进度只凭 task_id，不用重发催；
5. 同任务同一 contextId 并要求透传；
6. 派发超时 failed ≠ 未达：验现状，不重做。

**代码同步（真源端制）**：一端唯一主写，其余端只读 ff-only；历史重写三铁律（先归集再重写 / 看祖先链不看新旧 / 重写期间冻结）。

## 四、产出了什么（实证闭环）

1. 团队协议栈四层定稿并三方签核：记忆协作规范 / 文件共享协议 / 密钥交换 / 协作模式协议；
2. 协议自身首次实战闭环：一端巡检发现技能死指针缺陷 → 验证 → 修复 bump → 索引同步 → 回执确认；
3. 22 技能首批入库共享桶并完整性验收（差集核对抓出漏传 + 中文名文件）；
4. 记忆三端互联 + 双向闭环；
5. 代码仓 NAS bare 收口全链路（clone / 核对 / 旧仓归档）；
6. 跨端计数分歧实战闭环：一端报「文件数不符」→ 根因 git quotePath 给中文路径加引号 → 统一口径复测三端一致 → 坑固化进规范；
7. 通信协议 v2 迁移消费闭环（覆盖 + sha 校验 + 首发实测）。

## 五、有什么优势（对比单 Agent）

1. 24h 在线兜底；2. 三 OS 覆盖；3. 上下文隔离降偏见（防自我背书）；4. 跨端可复现性校验（他端能否按文档跑通）；5. 真源端制消冲突；6. 多端互验把误报 / 误判收敛。

## 六、扩展了什么场景

求职运营（分析 / 简历 / 打听各司其职）、跨端代码同步（不上公共托管）、团队技能分发、密钥安全交换、巡检 cron 前缀认领、新 Agent 入队规程。
